模块化工程总览：从来源文件到可签发成品

本地优先的书籍翻译与出版系统。扫描 PDF、文字层 PDF 和 EPUB 进入同一个依赖图（DAG），翻译后生成 EPUB、Word、知识库和参考 PDF，并由发布门决定是否 release_ready。本页数据基于 macos 分支 36c5331，均为静态统计或本机实际运行结果。

自上而下分为入口、运行时契约、编排、领域处理、本地模型五层。点击任一包，查看其中每个模块的职责、输入输出、关键符号和跨模块数据流。卡片底部色条表示代码行数占比。

包之间的 import 依赖

行是导入方，列是被导入方，格内数字是 import 语句条数，颜色越深耦合越强。runtime 被几乎所有包依赖；pipeline ↔ publication、pipeline ↔ knowledge 存在双向引用。

依赖图节点：三条输入路径

每个节点声明 requires 与 provides 两组 artifact，图中只画非冗余依赖，完整 requires 见节点详情。执行器按 stable_fingerprint(node, version, declared, requires) 计算指纹，命中 .pipeline_graph/state.json 且校验器通过时跳过。虚线框是可选节点。右上角徽标标出在节点内调用模型的位置（LLM / OCR / 嵌入）。用右侧开关切换“含可选节点”和“仅默认节点”：开启 OCR 校勘或翻译后，后续节点读取的页产物（current_pages）依次改为 pages.proofread、pages.translated。点击节点高亮它的上下游。

LLM 与模型客户端

所有模型调用都从 pipeline.toml 的档位（Profile）出发：档位里的 adapter 决定构造哪个客户端类，客户端再决定传输方式。远端文本模型都走 OpenAI 兼容的 {base_url}/chat/completions。客户端返回的 ModelIdentity（provider、adapter、model、base_url、thinking、提示词版本）进入缓存身份，换模型就会让对应页检查点或批次缓存失效。

本地模型：共享租约与托管生命周期

原生 PaddleOCR 和本地 llama.cpp 翻译（hy_mt2_local，Hy-MT2-1.8B Q4_K_M）共用一把用户级锁 ~/.translation-agent/paddleocr/cpu.lock，同一时刻只有一个重模型占用内存。先取租约再加载权重，后端退出后才释放。

发布门

报告只有在全部必需检查都通过、且检查顺序与 CHECK_IDS 完全一致时才是 release_ready。文件生成成功不等于可以交付。红框是本机当前运行中出现失败的检查。
